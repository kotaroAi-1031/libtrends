01結論サマリ

調査全体から言えることを 4 点に絞る。

① API は三層で組み合わせる

レジストリ公式（一次ソース）、deps.dev / ecosyste.ms（横断集約）、GitHub / Scorecard / OSV（付加指標）。 単一 API で全指標は揃わない。

② 履歴は分割して取り、範囲を明示する

npm の downloads API は 18 か月を超える要求を黙って切り詰める。実測で 27% の欠落。 取得はチャンク分割し、返ってきた期間を画面に出す。

③ 健全性は軸別に扱う

EOL は足切り、脆弱性は CVSS、保守性は連続値。人気度と混ぜると「人気だが EOL」を 高評価してしまう。

④ 欠損は 0 と区別する

取得できない値は null、判定不能は unknown。 実測値と推定値は別フィールドで保持する。

3 実装に共通する弱点

  • すべて npm 専用。PURL による名寄せもエコシステム差異の吸収もない
  • 健全性・脆弱性を指標に含めていない
  • ダウンロード数の意味（CI・ミラーを含む）の説明が弱い

「18 か月の壁」— 実測された欠落

npm downloads API は 18 か月を超える期間を要求すると、エラーにせず黙って切り詰める。 TanStack の検証では、18 か月・24 か月・全期間のどれを要求しても 549 日分の同じ値が返った。 @tanstack/react-query を単一リクエストで取った場合と、500 日ずつ分割して合算した場合の差は次のとおり。

TypeScript— 500 日ずつ分割して合算する（設計ブログのコードを要約）
const maxChunkDays = 500; // 18 か月上限を安全に下回る
while (currentDate < today) {
  const chunkEnd = addDays(currentDate, maxChunkDays);
  const url = `https://api.npmjs.org/downloads/range/${format(currentDate)}:${format(chunkEnd)}/${pkg}`;
  const data = await fetchWithRetry(url);   // リトライ必須
  chunks.push(data);
  currentDate = chunkEnd;
  await sleep(200);                          // レート制限回避
}
const total = chunks.flatMap(c => c.downloads).reduce((s, d) => s + d.downloads, 0);
設計への反映: 取得した期間が要求と一致したかを必ず検査し、不一致は meta.missing に記録して UI に出す。どの API でも「要求した期間」と「返ってきた期間」を 突き合わせる、というルールを共通化する。

合成ルール（案・推測を含む）

  • EOL は足切り。他指標で覆さない（例: request は今も広く使われるが EOL）
  • 脆弱性は CVSS を主、件数を従。確度の低い検出は除外
  • 保守性は連続値。0〜100 に正規化し、平均ではなく低い方を強調
  • 人気度は健全性と分離。混ぜると「人気だが EOL」を高評価にする

vuls の位置づけ

vuls は OS・サーバ寄りの脆弱性スキャナで、vuls report -format-json と CycloneDX 出力を持つ。ライブラリ横断の脆弱性ソースには向かないため、 スコアの主ソースにはしない。

用途は「利用環境の観測」と「検証済み知見の還元」に限定。レジストリ横断の脆弱性は OSV（API-018）を主とする。この環境に vuls は未導入で、実出力の検証は未実施。

06未決事項

調査では決めきれず、実装前に判断が必要なもの。

  1. スコア合成の是非と重み — 軸別表示のままにするか、単一スコアを出すか。検証方法も未定。
  2. 対象カタログの作り方 — 「人気上位 N 件」の N と選定基準。レジストリ間の偏り。
  3. PyPI のダウンロード指標 — 非公式 API-010 で始めるか、API-011（BigQuery）に投資するか。
  4. DL 数を持たないエコシステム — Maven（API-015）と Go（API-016）を被依存数だけで比較してよいか。
  5. レート制限が不明な API の運用間隔 — 実測で決める必要がある。
  6. vuls の組み込み範囲 — 初期リリースに含めるか。実機検証も未実施。
  7. データ鮮度の表示仕様 — 取得失敗時に古い値をどう見せるか。
  8. 利用条件の確認 — ecosyste.ms の商用条件、libraries.io のキー、crates.io のレート制限。
